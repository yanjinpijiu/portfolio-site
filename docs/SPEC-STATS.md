# SPEC：统计增强（归属地显示、按日期查日志、市级地图、下载来源）

> 这份文档回答三件事：现在哪里不对、要改成什么样、怎么算改完了。
> 只写设计和验收标准，不贴实现代码。所有「现状」都经过对代码和线上库的核对，不是推测。

## 1. 背景

### 1.1 现在能看到什么

后台「数据看板」是三个 tab，顶上一条 7 / 30 / 90 天的时间范围横条，聚合图表都吃这个范围。

| tab | 内容 |
|---|---|
| 访客 | 访问趋势、24 小时、星期、地区分布（中国地图·省级）、省份 TOP10、浏览器、系统、设备、页面分布、高频 IP、访问明细（最新 50 条） |
| 接口 | 调用趋势、慢接口、登录专项（趋势 + 失败来源 IP）、下载接口业务码分布 |
| 简历下载 | 下载趋势、每版下载量、按简历统计、下载来源省份、下载明细（最新 50 条） |

**明细表不吃饭时间范围横条**，它是写死的「最新 50 条」，没有日期筛选、没有翻页、没有检索。

### 1.2 四个问题

1. 高频 IP / 登录失败来源 / 下载明细三张表的「归属地」列，有一部分显示成 `—`。
2. 想看某一天的访问，只能翻最近 50 条，翻不到就没了。接口那块连明细表都没有。
3. 地区分布只能看到省，看不到市。
4. 简历被谁下载了、对方在哪儿、同一个人下了几次，现在看不出来。下载明细只有「最新 50 条」，翻不到更早的，也没法按 IP 搜。

### 1.3 线上数据量

这些数字决定了要不要上重型方案（预聚合、游标流式、分表）：

| 表 | 行数 | 时间跨度 |
|---|---|---|
| `visit_log` | 47 | 2026-09-15 21:58 起（两天） |
| `api_access_log` | 805 | 同上 |
| `resume_download_log` | 6 | 同上 |

量级是每天几十条访问、几百条接口调用。全文扫描、`LIKE`、`COUNT(*)` 在这个量级下都是毫秒级，所以下面的设计一律选简单的做法。

## 2. R1 归属地显示修复

### 2.1 现象

高频 IP 表里，`57.155.170.204`、`140.179.165.247`、`149.57.180.172` 的归属地显示 `—`，其他 IP 正常。

### 2.2 根因（已定案）

**不是没查到，是显示的时候把「国家」这一级丢掉了。**

我直接读了后端用的 `backend/src/main/resources/ip2region.bin`（502834 条区间、2423 个地名，全表无空洞，IPv4 空间 100% 覆盖），复现结果：

| IP | 库里查到的 | 现在显示 |
|---|---|---|
| `57.155.170.204` | 法国（只有国家级） | `—` |
| `140.179.165.247` | 中国（只有国家级，无省） | `—` |
| `149.57.180.172` | 美国（只有国家级） | `—` |
| `112.24.205.15` | 中国 / 江苏省 / 常州市 | 江苏省 常州市 |

归属地在埋点写入时就存进库了（`StatsCollector` 调 `IpRegionService.lookup`，三个字段一起入库）。问题出在展示层的 `StatsQueryService.joinRegion()`：它只拼 `province + city`，`country` 读出来直接扔掉，两个都空就返回 `null`，前端 `row.region || '—'` 渲染成横线。

线上 47 行里：40 行有省、37 行有市、6 行只有国家（就是上面那三个 IP）、1 行是 `127.0.0.1` 的内网（`city` 字段是「内网IP」）。`joinRegion` 同时被三处调用（高频 IP、登录失败来源 IP、下载明细），改一个函数三处一起好。

**还有一层数据本身的限制**：ip2region 的免费数据对境外 IP 基本只到国家，`法国` 和 `美国` 那两条连省都没有。这不是 bug，换显示逻辑也变不出省市来。

### 2.3 改法

`joinRegion` 改成逐级退化，并区分境内境外：

| 情形 | 显示 |
|---|---|
| 有省有市，境内 | `浙江省 温州市`（不重复标「中国」） |
| 有省无市，境内 | `浙江省` |
| 境外 | `美国 加利福尼亚 圣克拉拉` / `法国`（国名必须有，否则不知道是哪儿） |
| 只有国家，且是中国 | `中国` |
| 三个都空 | `—` |
| 内网 | `内网IP`（库里的原值） |

顺带修一个观感问题：直辖市的省市两级在 IP 库里是「北京」和「北京市」，港澳是「香港特别行政区」和「香港」，照原样拼出来是「北京 北京市」这种看着像 bug 的重复。两级互相包含时只留长的那个，其余照常拼（`浙江省 温州市` 不变）。

规则一句话：**境内 IP 不显示国名（省市已经够），境外 IP 一定显示国名；两级重复时只留一个。**

### 2.4 连带处理

地区分布地图和省份 TOP10 都是按 `province` 分组的，`province` 为空的行不会出现在图上。「中国但无省」的那一行就这样静默消失了，看的人会觉得总数对不上。

处理：这两张卡片的标题旁补一句「另有 N 条只解析到国家，未计入」（N 由一次 `COUNT(*)` 得出），信息不丢，也不污染地图。

### 2.5 验收

- 三张表里 `57.155.170.204` 显示「法国」，`140.179.165.247` 显示「中国」，`149.57.180.172` 显示「美国」。
- 国内的仍然显示「浙江省 温州市」这种两级写法，没有多出「中国」两个字。
- `127.0.0.1` 显示「内网」。
- 地区分布卡片上能看到「另有 6 条只解析到国家」。

## 3. R2 日志按日期查看

### 3.1 需求

把「最新 50 条」升级成能按日期检索的日志页，覆盖**访问日志和接口日志两张表**。核心诉求是排查问题：某天的访问为什么没被统计、某个 IP 都干了什么、某个接口为什么报错。

简历下载日志不进本期。它到现在总共 6 行，而且「最新 50 条」放得下。后端那套分页查询是通用的，到时候补一个 mapper 方法和一个表头配置就行——**第 5 节（R4）会把它加回来**，因为「谁下载了我的简历」这个需求绕不开按 IP 搜。

### 3.2 交互设计

**入口**：新增独立路由 `/admin/logs`（页面名「访问日志」），左侧导航加一项，放在「数据看板」下面；同时在数据看板的 tab 条右侧加一个「按日期查日志 →」的链接。独立成页而不是塞进看板的第四个 tab，是因为看板那个文件已经 760 行，日志页有自己的筛选状态和分页，混在一起会互相拖累。

**页面结构**（从上到下）：

1. 类型切换：访问 / 接口（两个按钮，切换时重置到第 1 页，筛选条件保留）
2. 筛选条：日期起止 + 快捷按钮（今天 / 昨天 / 近 7 天 / 近 30 天）、关键词输入框、路径下拉、页面类型下拉、国家 / 省 / 市三级联动下拉、浏览器 / 系统 / 设备下拉、接口专有的「仅看失败」和「包含后台自己」开关、右侧「导出 CSV」
3. 表格：列随类型变（见下）
4. 分页条：上一页 / 下一页 / 「第 X / Y 页」/ 每页条数（50 / 100 / 200）/ 「共 N 条」

各类型的表格列：

| 类型 | 列 |
|---|---|
| 访问 | 时间、路径、页面类型、IP、归属地、访客 ID、浏览器 / 系统 / 设备、来源 |
| 接口 | 时间、路径、方法、业务码、HTTP、耗时、IP、归属地、后台自己 |

访问表比现在多一列「访客 ID」——排查「这个人为什么没被统计」时要拿 cookie 里的 `pv_uid` 对着搜，现在这一列根本看不到。

**地区三级联动**：国家下拉列出范围内出现过的国家，选了「中国」之后省份下拉才列出省份，选了省之后市的选项再收窄到该省。三个都可以留空表示不限。境内和境外分开选，避免出现「国家=中国 + 省=俄勒冈」这种必然空结果的组合。

**筛选条件写进 URL query**（`type` / `from` / `to` / `page` / `q`），刷新不丢，也能 bookmark 一个「只看 09-16 温州来的访问」的地址。手机上排查问题时会用到。

### 3.3 接口设计

**查询**

`GET /api/admin/stats/logs`

| 参数 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `type` | `visit` / `api` | `visit` | 查哪张表 |
| `from` | `yyyy-MM-dd` | 今天 | 起始日，含当天 |
| `to` | `yyyy-MM-dd` | 今天 | 结束日，含当天 |
| `page` | ≥ 1 | 1 | 页码 |
| `size` | 1..200 | 50 | 每页条数，超出上限截断 |
| `q` | ≤ 64 字 | 空 | 关键词，匹配 IP / 访客 ID / 路径（`LIKE %q%`） |
| `path` | 字符串 | 空 | 精确匹配路径 |
| `pageType` | `home` / `projects` / `project` / `resume` / `other` | 空 | 仅访问 |
| `country` `province` `city` | 字符串 | 空 | 地区，精确匹配。**仅访问日志**：接口日志表里没有这几列，硬做会让分页数不准 |
| `device` `browser` `os` | 字符串 | 空 | 终端，精确匹配。仅访问日志 |
| `onlyFail` | 布尔 | false | 仅接口：`biz_code <> 0` |
| `includeInternal` | 布尔 | false | 仅接口：是否含后台自己发的请求 |

响应：

```json
{
  "type": "visit",
  "from": "2026-09-17",
  "to": "2026-09-17",
  "page": 1,
  "size": 50,
  "total": 47,
  "pages": 1,
  "counted": 41,
  "rows": []
}
```

`total` 是符合筛选条件的总行数，`pages = ceil(total / size)`。`counted` 只对访问类型有意义：符合条件但无法定位到省的行数，用来在表格下方提示「其中 N 条只解析到国家」。

**下拉候选项**

`GET /api/admin/stats/logs/options?type=&from=&to=`

返回所选类型在所选日期范围内实际出现过的值，用来填下拉框（不写死、不查全表）：

```json
{
  "paths": ["/", "/projects", "/resume"],
  "pageTypes": ["home", "project"],
  "regions": [{ "country": "中国", "province": "浙江省", "city": "温州市" }],
  "devices": ["PC", "手机"],
  "browsers": ["Chrome"],
  "oses": ["Windows"]
}
```

省和市两个下拉由 `regions` 在前端推导（选了省之后市下拉只列该省出现过的市），不用再做一次请求。各类候选项都限制在 200 项以内。

**导出**

`GET /api/admin/stats/logs/export`，参数与查询接口相同，忽略 `page` / `size`。

- 响应 `text/csv; charset=utf-8`，写入 UTF-8 BOM（Excel 打开中文不乱码），逗号分隔，字段里的逗号、引号、换行按 RFC 4180 转义
- 文件名 `logs-{type}-{from}_{to}.csv`。用 ASCII 不用中文：中文名虽然能靠 RFC 5987 编出去，但不同浏览器和解压工具的处理不一致，一个日志文件不值得为这个赌
- 上限 5 万行，超出截断，末尾补一行 `# 结果超过 N 行，已截断`
- 前端走 `fetch` + `blob`（和现有的「导出备份」一样，令牌走请求头，普通链接带不上）

### 3.4 查询实现

三个 mapper 各加两个方法：一页数据、一个总数。写法用 MyBatis 注解里的 `<script>` + `<if>` 动态拼 SQL（这个仓库目前没有 XML mapper，也没配 `PaginationInnerInterceptor`，不为了这个功能引入）。

- 时间条件统一走 `visit_date BETWEEN #{from} AND #{to}`，不按 `created_at`。`visit_date` 是入库时按服务器本地日期算好的（服务器时区 CST），和日历日一致，而且三张表都有这一列
- 排序 `ORDER BY id DESC`，和「最新 50 条」的口径一致，同秒写入时顺序也稳定
- 分页 `LIMIT #{size} OFFSET #{offset}`，配一条同样 WHERE 的 `COUNT(*)`
- 关键词用 `#{}` 绑参，`%` 在 Java 侧拼进参数值。绝不用 `${}` 拼接（那是注入）

**索引**：`api_access_log` 目前只有 `created_at` 和 `(path, created_at)` 两个索引，按 `visit_date` 过滤没有索引可用。补一条 `CREATE INDEX IF NOT EXISTS idx_api_date ON api_access_log (visit_date)`，和另外两张表对齐。

### 3.5 不做的事

- **不做日志保留期清理。** 三张表里只有 `api_access_log` 是持续增长的，按现在的量级一年十几万行，H2 单表完全撑得住；自动删历史反而会丢掉排查用的数据。等单表接近 50 万行再考虑加清理任务，这个阈值写进 README 的「已知边界」。
- **接口日志不给地区筛选。** `api_access_log` 只存了 IP，没有国家 / 省 / 市这几列，也没有页面类型。「归属地」列是查询时现查内存表补上的（只影响显示），要在这一列上筛选就得先把整段时间的数据捞进内存再过滤，分页数会失真。真需要按地区筛接口日志，先给那张表补字段并回填历史——不是这一期的事。
- **不做跨表关联。** 比如在访问明细里显示「这个访客当天还下载了简历」——现在数据量小，真要看就按访客 ID 搜一次，两边都能搜到。
- **不做实时刷新 / 自动轮询。** 看板本来就是刷新看一次。

### 3.6 验收

- 打开日志页默认是「访问 / 今天 / 第 1 页」，表里行数与该日 `visit_log` 的实际行数一致（用服务器上的 SQL 核对）。
- 翻到第 2 页，内容和第 1 页不重叠；到最后一页时「下一页」置灰。
- 日期切到 09-16，行数与该日实际行数一致。
- 搜某个 `pv_uid` 能查出这个访客在范围内的全部记录。
- 选「浙江省」之后，市下拉只剩该省出现过的市。
- 看板上的「访问明细（最新 50 条）」点「查看全部」能带着日期跳到日志页。
- 导出 CSV 用 Excel 打开，中文不乱码；行数等于页面上显示的「共 N 条」（未截断时）。
- 手工请求 `size=1000`，服务端按 200 处理（上限生效）。
- 关键词传 `' OR 1=1 --`，返回 0 行而不是全部（绑参生效）。

## 4. R3 市级地图

### 4.1 数据现状

后端 `/api/admin/stats/visits` **已经返回了市级聚合**（`city` 字段，`[{province, city, pv, uv}]`），只是前台没用。现在的使用情况：

- 有市的行 37 / 47，去重后 6 个城市（温州、常州、佛山、上海、北京、圣克拉拉）
- 前端已有一份 `frontend/src/assets/china-geo.json`：582KB、34 个省级面，DataV GeoAtlas 格式（`properties` 里有 `adcode`、`name`、`center`、`centroid`、`level`）
- `ChartBox.vue` 只在 `series-type="map"` 时按需加载这份 GeoJSON，只有打开看板才会下载

### 4.2 调研结论（实测，2026-09-17）

**现有那份 `china-geo.json` 就是 DataV 的 `100000_full.json`**：实测该 URL 返回 582,522 字节，和仓库里的文件一模一样。这一点很重要，它决定了下面哪个方案跟现状最一致。

| 来源 | 要素数 | 原始体积 | gzip 传输 | 许可 | 备注 |
|---|---|---|---|---|---|
| DataV `100000_full.json`（省级，已用） | 34 | 582 KB | 201 KB | 无正式声明 | 数据版本约 2021 年中 |
| DataV 各省 `_full.json` 合并（全国市级） | 476 | 约 3.7 MB | 约 1.19 MB | 无正式声明 | 需自己写合并脚本；名字带全后缀 |
| 同上，只留 369 个市级单元 | 369 | 约 3.35 MB | 约 1.11 MB | 同上 | 直辖市当一个单元，港澳台单列 |
| `echarts@4.9.0/map/json/china-cities.json` | 367 | 1,207,956 B | 710,201 B | Apache-2.0 | 边界是 2016 年前后；名字不带「市」后缀；`feature.id` 就是 6 位 adcode |
| DataV 单省，如 `330000_full.json` | 11 | 120 KB | 41 KB | 无正式声明 | 下钻方案要 34 个这样的文件 |

几个关键事实：

- `geo.datav.aliyun.com/areas_v3/bound/{adcode}_full.json` 目前**可以直连**，返回 `Access-Control-Allow-Origin: *`，路径规则是 `{adcode}.json`（单个面）/ `{adcode}_full.json`（含下级）。区县没有 `_full`（404），不设区的地级市（东莞 `441900`、嘉峪关 `620200`）也没有。
- DataV **没有现成的「全国市级」文件**，只有省级。要做全国市级必须自己合并 33 个省。
- `echarts@6.1.0` 的 npm 包里**不含任何地图文件**，地图必须自备后 `registerMap`。
- echarts 4.9 那份地图是压缩编码格式（`UTF8Encoding` + `encodeOffsets` 字符串坐标）。已核对 ECharts 6 源码，解码逻辑还在，能直接用；但别的库（Leaflet、MapLibre）读不了。
- 第三方现成的全国市级 GeoJSON（如 `Chriszkxxx/geojson-map-china-cities`，4.6 MB、520 要素）有重复要素且没有 LICENSE，只作兜底。
- npm 上没有「自带全国市级 GeoJSON 且体积可控」的包：要么 `echarts@4.9.0`，要么 `echarts-china-cities-js`——后者解包后有 361 MB（1987 个文件），不能 `npm i`。

### 4.3 选型（已定稿并实现）

**用 AreaCity 的省市区边界数据自己编译一份全国市级底图。**

第一轮调研里体积最小的是 `echarts@4.9.0` 那份，但它的边界停在 2016 年、名字不带「市」后缀，跟 ip2region 解析出来的城市名对不上，用户当时的反馈也是「找更详细的」。第二轮专门去找了更高精度的源，实测对比：

| 数据源 | 市级要素 | 总坐标点数 | 平均点/市 | 原始体积 | gzip | 数据年份 |
|---|---|---|---|---|---|---|
| **AreaCity ok_geo（采用）** | 372 | **349,613** | **940** | **3.99 MB** | **1.19 MB** | 2026-04 |
| AreaCity 原始（未简化） | 372 | 2,213,273 | 5,949 | 43.6 MB | — | 2026-04 |
| DataV 33 省 `_full` 合并 | 363 | 140,494 | 387 | 3.29 MB | 1.09 MB | 2021 |
| GADM 4.1 CHN ADM2 | 368 | 252,742 | 686 | 4.85 MB | 1.41 MB | — |
| `echarts@4.9.0` china-cities | 367 | —（压缩编码） | — | 1.21 MB | 710 KB | 2016 |

AreaCity 那份 10% 简化后，体积和 DataV 相当，坐标点数是它的 2.5 倍，数据新 5 年，还多了台湾的县级单位（虽然边界字段是空的，见下）。

**数据来源与许可是这次选型的关键**：仓库 `xiangyuecn/AreaCity-JsSpider-StatsGov`（6884 star，MIT，2026-04 仍在更新）。上游数据是国家地名信息库 2025-12-31 + 高德/腾讯行政区划采集。MIT 覆盖的是代码和转换工具，不覆盖上游数据本身；个人非商用站点用没问题，商用要另行确认。

**为什么不选 GADM**：点数只比 DataV 多 1.8 倍，而且它对藏南、阿克赛钦、台湾的画法有自己的立场，中文站点用有政治风险。

**为什么不选高德/腾讯的 REST 接口**：要实名申请 key，且官方文档明确 `extensions=all` 只返回当前查询区域的边界、不返回下级，拿全国 340 个市要发 340 次请求并受配额限制。不适合做离线底图。

**为什么不选下钻**：34 个省文件合计约 4 MB 进仓库，比一张全国图还重，还多一层交互状态。这个站目前只有几个城市的数据，下钻解决不了实际问题。

### 4.4 怎么生成的

数据源是 16.5 MB 的 7z（解出 159 MB 的 CSV，3635 行，deep 0/1/2 分别是省/市/区县）。

```bash
# 1. 下数据。GitHub Releases 直连不通（302 之后断），走镜像或代理
curl -x http://127.0.0.1:7890 -L -o ok_geo.csv.7z \
  https://gh-proxy.org/https://github.com/xiangyuecn/AreaCity-JsSpider-StatsGov/releases/download/2025.251231.260403/ok_geo.csv.7z

# 2. 解压（py7zr，pip install py7zr）
python -c "import py7zr; py7zr.SevenZipFile('ok_geo.csv.7z').extractall('./okgeo')"

# 3. 编译成 GeoJSON（工具在仓库里，见 tools/build_city_geo.py）
python tools/build_city_geo.py okgeo/ok_geo.csv --out /tmp/china-cities-raw.json

# 4. 简化。这一步很关键：不简化是 43 MB
npx --yes mapshaper@0.7.61 /tmp/china-cities-raw.json -simplify 10% keep-shapes -o precision=0.0001 \
  frontend/src/assets/china-cities-geo.json
```

`mapshaper` 用 `keep-shapes` 做拓扑保持简化，相邻城市共享的边界不会裂开；`precision=0.0001`（4 位小数，约 11 米）再省掉一批没意义的尾数。10% 这一档在杭州的实测偏差是均值 138 米、最大 1.4 公里——全国地图上一个像素是公里级，肉眼看不出，要更精细可以把比例调到 20%。

**产物两份**：

| 文件 | 体积 | 谁用 |
|---|---|---|
| `frontend/src/assets/china-cities-geo.json` | 4.0 MB | ECharts 按需加载（只有打开看板并切到「按市」才会下载） |
| `frontend/src/assets/china-cities-names.json` | 5 KB | 名单，给页面做城市名归一用，直接静态引入 |

**台湾的 20 个县市在源数据里 `polygon` 字段是 `EMPTY`**，所以最终 372 个要素不含台湾的市。省级地图上台湾仍然是一个完整的省。这是免费数据的分级限制（作者把乡镇级做成了付费数据），不是解析出错。

### 4.5 真正的工程量在名字对齐

ECharts 的 `series.map` 默认**按名字严格匹配**，对不上的直接不显示（省份图那边早就有个 `mapName()` 在处理同样的问题）。ip2region 的城市字段多数是「杭州市」这样的全称，和底图直接对得上；对不上的是这三类：

| 情况 | ip2region 给什么 | 底图里是什么 |
|---|---|---|
| 自治州 | `延边`（没有后缀） | `延边朝鲜族自治州` |
| 地区 / 盟 | `阿里`、`锡林郭勒` | `阿里地区`、`锡林郭勒盟` |
| 直辖市的省和市同名 | 省 `北京市`、市 `北京市` | `北京市`（对上，但归属地显示要去重） |

处理方式在 `cityName()`：先查名单，再试补 `市 / 自治州 / 地区 / 盟` 四个后缀，最后拿简称去前缀匹配那三类全称。都不行就原样返回——那个市在地图上亮不起来，但下面的排行榜里还在，不会静默丢数据。

另外两处细节：

- **「内网IP」要排掉**。私有地址在 IP 库里拿到的城市字段就是「内网IP」，它不是地名，出现在「城市 TOP10」里很怪。
- **色阶上限只按能落到地图上的城市算**。不筛的话，一个画不出来的城市会把上限拉高，结果所有画得出来的城市都挤在最浅的一档，整张图看着像没数据（这个在本地实测时一眼就看出来了）。

### 4.6 验收（已逐条验证）

- 地区分布卡片能切「省 / 市」两档，切到市是全国范围的市级面填充，按市着色。✓
- 「省份 TOP10」跟着档位变成「城市 TOP10」。✓
- 切档时 `ChartBox` 会换成新实例（靠 `:key`）：不然 echarts 和地图注册是缓存的，市级底图永远不会被注册，图会空着。✓
- 高亮不起来的城市，在排行榜里仍然能看到。✓
- 公开页面（首页、项目页、简历页）的构建产物里不出现这两份 GeoJSON，也不出现 echarts；市级底图是独立的 chunk，只有切到「按市」才下载。✓
- 地图 tooltip 在没数据的区域显示「0 次」而不是「NaN 次」（ECharts 给的是 NaN，`?? 0` 挡不住）。✓

## 5. R4 简历下载的来源

### 5.1 现在能看到什么

简历下载 tab 上有：下载趋势、每版下载量、按简历统计（下载次数 / 下载人数 / 免验证 / 过验证码）、下载来源省份、下载明细（最新 50 条，已经有 IP 和归属地两列）。

`resume_download_log` 在写入时就把 `country / province / city` 和 `visitor_id` 一起存了（和访问日志共用同一套归属地解析），所以按 IP、按地区聚合需要的数据是现成的，缺的只是把它查出来、显示出来。

### 5.2 要加什么

**① 「下载来源 IP」表**（看板「简历下载」tab）

一句话回答「是哪个 IP 下的、在哪儿、下了几次」：

| IP | 归属地 | 下载次数 | 独立访客 | 下载过几份简历 | 最近一次 |
|---|---|---|---|---|---|

- 按下载次数降序取前 20
- 「归属地」走的是 R1 那个 `joinRegion`，所以省级缺失时会退化到国家，境内显示到市、境外带国名
- 「独立访客」= `COUNT(DISTINCT visitor_id)`。同一出口 IP 下换台机器/换个浏览器就是两个人（公司、学校的出口 IP 很常见），这个数能区分「一个人下了 5 次」和「五个人各下了 1 次」
- 「下载过几份简历」= `COUNT(DISTINCT resume_id)`。一眼看出这个人是对着某个岗位来的，还是在广撒网

**② 下载来源地区细化到市**

现在只有一张「下载来源省份」条形图。跟 R3 的市级底图共用一套地区展示：省 / 市两档切换，或者直接把市级数据画进同一张图。

市级数据不用额外查一次：把现有那条 `byProvince` 改成 `GROUP BY province, city`，一次查出来，前端按档位取用。

**③ 把下载日志接进日志页（第三类）**

第 3.1 节把简历下载排除了，理由是它总共只有 6 行。但「是哪个 IP 下的」这个问题一旦问出来，下一个问题必然是「这个 IP 还下过别的吗、什么时候下的」——那正好是日志页的活。

把 `type=download` 加回去：后端照抄 `pageLogs` / `countLogs` 那套写法加两个方法，前端多一组表头配置，改动大约三十行，不值得为它单开一个页面。表格列：时间、简历、方向、IP、归属地、访客 ID、放行方式。

### 5.3 数据量的现实

线上这张表现在只有 6 行，所以①里「前 20」实际上就是一两条，②的市级分布也基本只有一两个市。这一节的实现价值不在现在，在于把口径和入口先建好——等简历投出去之后，回来看「谁下的、下了几次」是能直接看懂的，不用临时再改代码。

### 5.4 验收

- 「下载来源 IP」表里每个 IP 的下载次数之和，等于同期「按简历统计」里下载次数之和（两条查询口径一致才算对）。
- 同一个 IP、不同 `visitor_id` 的两条记录，在这个表里合并成一行，独立访客显示 2。
- 归属地显示规则和第 2 节一致：境内到市、境外带国名、解析不出来是 `—`。
- 日志页切到「下载日志」能按日期翻、按 IP 搜，行数和 `resume_download_log` 里同期的行数一致。
- 下载来源地区切到「市」档，显示的市和明细里的市对得上。

## 7. 风险

- **`visit_date` 依赖服务器时区。** 服务器是 CST，JVM 没显式配时区，取的是系统默认。如果以后把服务器搬到 UTC 或者 Docker 里没挂时区，`visit_date` 会整体偏 8 小时，日志页按日期查出来的结果就会错位。这个风险现在就存在（每日趋势图同样受影响），不是本次引入的。
- **关键词 `LIKE %q%` 用不上索引。** 现在几十行无所谓，行数上到几十万时这个查询会全表扫。那时候再说，不在本期优化。
- **CSV 导出是一次性查出来的**，5 万行上限下最坏情况占到几十 MB 内存。后端堆是 384MB，够用但不宽裕；如果以后真导出到上限，改成游标逐行写。
- **R3 的底图许可。** AreaCity 仓库是 MIT，但**上游数据是国家地名信息库 + 高德 / 腾讯的行政区划**，MIT 不覆盖数据本身；个人非商用站点用没问题，商用要另行确认。另外公开站点展示中国地图涉及审图号，这个站的地图只出现在需要登录的后台，风险很低，真要在公开页面用就得另行评估。
- **R3 的坐标系。** AreaCity 这份和现有的 `china-geo.json` 都是 GCJ-02，叠加没有偏移问题；换成 WGS-84 的瓦片底图才需要做转换。
- **R3 的名字归一需要长期维护。** 行政区划调整（撤市设区、更名）会让 `cityName()` 的后缀规则慢慢失效。归一失败的兜底是「排行榜照常显示」，不会丢数据；真维护不动了就让后端在编译 IP 库时顺带算出 adcode，按代码关联彻底绕开名字问题。
- **R3 的底图要重生成才有新数据。** AreaCity 每年更新几次，想跟上得重跑一遍 `build_city_geo.py` + mapshaper。这是有意的：底图进仓库、构建不依赖外网，代价是更新要手动来一次。
